# Hillock gaps against Aimee capabilities

Assessment: 2026-10-08, upstream revision `1edd166ead75b85a9ab95cd6ba4faf7011ad567c`. This is a source-based assessment plus isolated reproductions, not a claim about every upstream version or a full model-quality evaluation. The [exposure contract](FULL_SUPPORT_CONTRACT.md) describes possible interfaces; this assessment determines which capabilities we actually need and who owns them.

A **must-have** is necessary for correct supported memory/chat behavior. A **nice-to-have** is an additional retrieval/learning capability we can defer. **Conditional must-have** means a control becomes mandatory when its associated optional feature is enabled. Route names are proposals: the capability matters more than a particular HTTP layout.

## Replaceability is the acceptance boundary

The user clarified that native, Cognee and Hillock must be replaceable durable memory backends. Cognee/Hillock now use independent adapter-owned durable catalogs for canonical CRUD, revisions/history, scoped listing, retry receipts and erasure. The production constructor does not open native PostgreSQL memory storage. These baseline semantics are implemented; portable native record/history migration is implemented; optional feature parity and production-scale qualification remain pending.

The selected backend must own durable records and metadata; Aimee keeps authorization, policy, review, audit orchestration and chatbot composition. A backend-owned compatibility layer is acceptable where upstream lacks primitives, but hidden dependence on native memory storage is not. Aimee does not need to surrender its policies to an engine to replace its storage.

Additional **must-haves for replacement**: durable canonical CRUD and paginated listing; stable IDs and source/revision metadata; required conditional mutation/history semantics; verified erasure/restore; backend-neutral export/import; and one conformance suite proving each alternative works without the native memory record store. This changes the earlier retrieval-only assessment: canonical storage is not optional for the selected backend, while copying Aimee's policy decisions into Hillock remains unnecessary.

## Which findings are shared with Cognee?

The original shipping recall/briefing/export and post-erasure admission failures were shared Aimee adapter/catalog defects, now repaired. The former 256-record corpus refusal is replaced by whole-catalog lexical candidate selection: 16 synchronous Cognee candidates or 256 Hillock candidates per request. Native deadline and evaluation cleanup failures belong to Aimee's native/evaluation owners, regardless of which guest ran them. Native is not required to implement this external integration contract.

Confirmed on Hillock's pinned source: replacement of original relation `source_doc`, name-part linking of person/mountain entities, and the missing greeting method. The deployed stateless sidecar does not use those paths. Its subword/HYDRA profile and additional token/vocabulary/10-second compute bounds differ from Cognee's indexing path. We did not qualify Cognee's graph/extractor against the corresponding source/identity fixtures, or compare real-model answer quality; do not imply Cognee is proven free of analogous errors. The selected backend must implement canonical storage and required history/lifecycle primitives; it does not duplicate Aimee's authorization, audit, review or privacy policy orchestration. The existing owners invoke equivalent primitives through the backend contract.

## Nice-to-haves, with mandatory controls if enabled

| Optional capability | Potential benefit / current shortfall | Mandatory control if enabled |
|---|---|---|
| TALON model-based extraction | May reduce curator cost/latency; current output drops message attribution and original source offsets and ingestion directly commits triples. | Provenance-bound extraction proposals, unit/negation/uncertainty handling and human/host review before authoritative promotion. | GloVe/semantic HDC retrieval | Could retrieve paraphrases better than the POC's subword profile. | Multi-hop graph reasoning | May help relation queries across several claims. Stored reservoirs lack per-contribution source revision/lifecycle metadata. | Explainable supporting paths, inferred-versus-asserted distinction, exact provenance and correction/erasure of every dependent contribution. |

| Persistent derived indexes and async jobs | Avoid recomputing vectors and enable larger workloads. Not needed for a bounded stateless ranker that meets its workload. | Atomic generations, idempotent updates, backpressure, verified deletion, durable job status and erasure-safe restore. |

## Recommended sequence

1. Keep native as the default. The independent compatibility catalog and real-engine tests establish baseline replacement, not production-scale qualification or retrieval superiority.
2. Retain the completed conversation/transfer profile and qualify representative scale and real answer quality; add optional lifecycle profiles only when corresponding features are enabled.
3. Implement and compare the conversational must-haves in Aimee: durable episodes/projection, exact speaker/entity/unit lineage and intent-aware context assembly using existing served views. Freeze the Discord failures as answer-level trajectories.
4. Qualify Hillock on those same trajectories and a representative corpus. Address source/identity/lifecycle interfaces before enabling its extraction or persistent graph/learning state.
5. Add optional semantic/graph/Hebbian features only when measured answer quality, latency or cost improves. Do not make a missing optional feature a prerequisite for ordinary bot conversation.
