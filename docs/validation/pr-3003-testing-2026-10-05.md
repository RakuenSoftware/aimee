## Dedicated guests hold synthetic state

CT9210 (`aimee-pr3003-fresh`) and CT9211 (`aimee-pr3003-upgrade`) were created on
`192.168.1.253` for this validation. Each uses Debian 13, six CPU cores, 10 GiB RAM,
an unprivileged namespace and a 48 GiB thin volume on `storage`. Docker runs inside
the CTs with nesting and keyctl enabled. The deployment matrix publishes no host
ports; client-management tests bind only CT loopback. Stores and model fixtures
contain synthetic records. No production application or store is upgraded.

Proxmox initially refused CT creation because its configuration database had
aborted a transaction after a disk-full event. A consistent database backup
passed its integrity check before the configuration service restarted. Guest
processes remained running. CT storage and staging avoided the nearly full host
root filesystem.

The first Docker deployment attempts failed before application startup because
the CTs inherited an 8 MiB memlock ceiling. The shipped composition requests
1 GiB. Setting `lxc.prlimit.memlock: 1073741824` on these two CTs and restarting
them allowed the unchanged composition to start. Those attempts are setup
failures; they are not counted as passing application tests.

## Cognee startup blocks promotion

The [published-image driver](../../scripts/validation/release/cognee-image.py)
starts real Cognee 1.6.2 with disposable SQLite, LanceDB and graph state, plus
local deterministic completion and embedding fixtures. The provider authenticates
its disposable account. Its bearer token enters Aimee through Vault bootstrap
stdin, rather than container metadata. A Docker-host bridge proxy exposes the
provider only inside CT9210.

The unchanged published KB image does not become healthy within 240 seconds.
Its supervised memory child repeatedly reports:

```text
memory module unavailable: memory: derived erasure replay: memory: backend unavailable
```

No dataset request reaches Cognee. A second run reproduced the startup failure.
After that reproduction, a diagnostic wrapper in the disposable container
recorded the helper's parent-executable lookup failing with exit 1. The wrapper
recorded no credential bytes. The original image digest was unchanged; this
instrumented container is diagnostic evidence, not a passing application run.
See the [failed gate](pr-3003-testing-2026-10-05/cognee-image.json)
and [boundary diagnosis](pr-3003-testing-2026-10-05/cognee-boundary.json).

The source explains the failed boundary:

1. The [egress attach hook](../../server-go/cmd/aimee-module/main.go) calls
   `hardenEgressCredentialOwner`, making the process non-dumpable before requests.
2. The [Vault resolver](../../server-go/modules/egress/secret_resolver.go) then
   launches the credential helper when memory requests its opaque handle.
3. The [helper's parent attestation](../../src/modules/vault/vault_env_bootstrap.c)
   reads `/proc/<parent>/exe`. Linux refuses that lookup against the non-dumpable
   egress parent, so the helper fails before returning a credential.

The existing memory-backend egress unit test substitutes the resolver's helper
function. It verifies origin and handle policy but misses this real process
boundary. CI success therefore does not qualify published Cognee startup.

Repair the credential handoff while preserving non-dumpability and caller
attestation, add a real helper-boundary regression, publish the repaired testing
image, and rerun this gate. Real derived retrieval, outage-aware erasure,
idempotent retry and restored-state replay remain unvalidated by this image
because the test stops at startup. Do not count them as passes.

## Retained state and qualification limits

Both owned CTs are stopped after validation. CT9211 retains the matched
`published046-20261005` snapshot; CT9210 retains private diagnostics. The report
and public verdicts are on the validation branch, leaving the tested `testing`
head unchanged. The main promotion remains a draft with its existing approval
gate.

The local checks use ordinary PostgreSQL storage. The promotion CI passed its
encrypted deployment, recovery and migration gates separately. These CPU-only
CTs do not rerun the three native model plugins on a GPU. Their separate signed
release retains its own publication and model-serving evidence requirements.

Private provider logs, Vaults, SQL credentials, client keys and account state stay
in the CTs. Published evidence contains image identities and fixture verdicts.
