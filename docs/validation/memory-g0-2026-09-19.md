Date: 2026-09-19. PR: [#2983](https://github.com/RakuenSoftware/aimee/pull/2983).

The release implementation at `50a4837e28f435ed37efd9aaaca3ed9fbff7a069`
passed fresh deployments, private/shared placement and failure tests, real-model
semantic recall, concurrency and exact-ID exploration, and published 0.4.1
upgrade/recreation/rollback on `.253`. One pure-Go memory owner serves both
placements; its producers/consumers use the existing C bus. The bus remains C.

## Bugs found and repaired

- Recall previously transported an owner failure with HTTP 200. The Server now
  preserves the owner's declared failure status in both placements. Shared
  invalid-confidence refusals also use the same HTTP classification as private
  memory, instead of becoming generic HTTP 502 errors.
- Large IDs were rounded by the CLI's numeric argument and response conversion.
  Memory ID arguments now retain decimal strings; JSON transport preserves exact
  large integer tokens for memory responses. Plain-text `memory get` also reads
  the Go envelope and prints the exact ID and full content. Native sanitizer
  regressions and the fresh HTTP/CLI/MCP fixture cover the boundary above 2^53.
- PostgreSQL pool initialization permanently cached its first failure. An upgrade
  could remain unavailable after the startup credential/TLS condition recovered.
  SQL and migration pools now cache only successful initialization and serialize
  retries. Race tests cover a TLS certificate arriving after the first attempt,
  concurrent recovery, and credential revalidation. The published upgrade passes
  without a manual provider restart.
- Clean CI exposed stale native sanitizer link dependencies, retired registration
  baselines and formatting. These were repaired. The whole-history secret scan
  retains exact false-positive fingerprints for two SHA inputs and the historical
  test PEM marker, with no path-wide exemption.

These are the original G0 release measurements. The subsequent
[performance follow-up](memory-performance-2026-09-20.md) records the optimized
Go implementation, fresh paired measurements and unchanged retrieval rankings.

| Metric | Pre-G0 baseline | Go candidate |
|---|---:|---:|
| MRR | 0.7429 | 0.9698 |
| Recall@5 | 0.7381 | 1.0000 |
| NDCG@5 | 0.7392 | 0.9777 |
| Recall@10 | 0.7381 | 1.0000 |
| NDCG@10 | 0.7392 | 0.9777 |
| Request latency p50 (ms) | 204.2 | 387.4 |
| Request latency p95 (ms) | 251.1 | 446.1 |

The candidate improves retrieval quality on this corpus, but increases request
latency: p50 is 1.90x and p95 is 1.78x the baseline. This is a measured cost,
not performance parity. The [full paired receipt](memory-g0-2026-09-19/paired-retrieval.json)
retains every query, including warmup, rather than only these aggregates.

The harness uses the frozen 50-fixture, 105-query corpus (SHA-256
`a38aacb1d4cd9d925f0d16d63f73bbc31fda2da72c7b2dd9bba7ffc662bfea01`), the
same real Bekko-a25m model at 384 dimensions, full raw queries, `scope=all`,
`limit=20` and each implementation's default ranking. The baseline is the pinned
merge base `bedabac667c5c00f9f14fe6f47efd3b369a46922`, built with the same
shipping Dockerfile options. PostgreSQL and model images are identical across
arms. Both applications run in the same guest.

Each arm persists all 50 real whole-record embeddings. The candidate also creates
965 derived units and activates a verified named embedding version for its 1,015
points. The baseline uses its supported `memory.embed` operation; the candidate
waits for durable indexing to drain and completes `reembed_start`/cutover. There
is no silent lexical substitute for absent vectors. The receipts preserve all
preparation responses, schema hashes, creation-time ranges, image identities,
harness hash, rankings and request timings.

One 105-query warmup per arm is excluded from the summary. Three measured rounds
alternate arm order, giving 315 measured queries per arm. Completed topology,
upgrade and exploratory stacks were stopped before the final timed run; no
application build overlapped it. The first diagnostic pair overlapped a build
and is not the release timing result.

Latency includes the identical Python/Docker-exec/public-KB-HTTP request boundary
on both arms. This small synthetic corpus is not a production workload or a
statistical performance certification. Fixture creation times are recorded but
not normalized; temporal/adversarial reproducibility remains part of MR-18.
Historical ranking equality is intentionally not a migration contract.

The follow-up below establishes that the baseline public route already used Go
lexical/graph retrieval and did not consume those stored vectors. This is a
comparison of different serving pipelines, not equivalent C-versus-Go work.
The original “native baseline” label was inaccurate.

## Latency attribution follow-up (2026-09-20)

The main cause is the added, serial **versioned semantic retrieval stage**. The
baseline C adapter already delegated `memory.find_facts` to Go `Search` or
`SearchVisible`; that version ended with lexical/graph retrieval and had no
shared semantic fusion. Seeding its embeddings did not make this public route
use them. Consequently, neither the quality gain nor the latency increase should
be attributed to the implementation language alone.

Temporary timing probes in the disposable candidate's Go owner measured five
warmups followed by all 105 corpus queries. The same public HTTP requests ran on
the retained baseline. A second candidate build bypassed only
`fuseSharedSemantic` as a diagnostic control, with all other code unchanged.
This bypass is not a proposed production change. The shipping binary was restored
and a successful public retrieval verified afterward; both owned stacks were
stopped again.

| Follow-up request timing | Baseline | Candidate | Candidate with semantic stage bypassed |
|---|---:|---:|---:|
| Mean HTTP time, excluding Docker overhead (ms) | 139.1 | 328.5 | 128.0 |
| P95 HTTP time, excluding Docker overhead (ms) | 185.8 | 398.7 | 172.3 |
| P95 including Docker overhead (ms) | 269.9 | 494.1 | 234.7 |

Candidate semantic-stage mean time was **187.3 ms**, versus a **189.4 ms** mean
HTTP increase over baseline. Bypassing that stage removes the regression. The
follow-up tail timings differ from the original release run; these are separate
measurements, and sums of stage percentiles would not be a valid attribution.

| Added semantic work | Mean wall time (ms) |
|---|---:|
| Rebuild lock, active version, stored identity and settings reads | 44.1 |
| Two live embedder identity probes, before/after embedding | 43.7 |
| Query embedding | 53.8 |
| Whole-record vector retrieval | 17.9 |
| Derived-unit vector retrieval | 27.7 |
| In-memory merge/finalization | <0.1 |

These are wall times at the owner, including PostgreSQL/egress service round
trips, not SQL CPU or model inference in isolation. Identity probes call the
embedder `/health` twice on every semantic query. Metadata and vector reads are
serial PostgreSQL module calls. The unchanged C bus carries those calls; this
measurement does not demonstrate a Go runtime slowdown or isolate bus polling
as the dominant source.

Optimization should target this request path: combine redundant metadata/policy
reads, avoid separate identity round trips through an equally strong identity
contract, and optimize vector queries while preserving current-input, audience
and lifecycle checks. Removing the semantic lane would also remove the new
retrieval capability, so the bypass is only causal evidence.

[Raw stage timings and control receipts](memory-g0-2026-09-19/latency-attribution.json)
contain every query timing and stage observation. They exclude credentials and
query content. The source path is `shared_recall.go:fuseSharedSemantic`, with
`unit_recall.go:unitSemanticCandidates` supplying the derived-unit lane.

## Reproduction

With the three images already built/pulled, export `AIMEE_APPLICATION_IMAGE`,
`AIMEE_POSTGRES_IMAGE` and `AIMEE_EMBEDDER_IMAGE` to their immutable references.
Run each topology against fresh storage:

```sh
python3 tests/e2e/deployment-matrix.py --topology T1 --output /tmp/g0-t1
python3 tests/e2e/deployment-matrix.py --topology T2 --output /tmp/g0-t2
python3 tests/e2e/deployment-matrix.py --topology T3 --output /tmp/g0-t3
python3 tests/e2e/kb-upgrade-e2e.py --storage plain --output /tmp/g0-upgrade
python3 tests/e2e/memory-paired-retrieval.py \
  --baseline "$BASELINE_IMAGE" --baseline-revision bedabac667c5c00f9f14fe6f47efd3b369a46922 \
  --candidate "$AIMEE_APPLICATION_IMAGE" --candidate-revision 50a4837e28f435ed37efd9aaaca3ed9fbff7a069 \
  --output /tmp/g0-paired
```

The paired runner must be timed without other test/build workloads. It tears down
its own stacks by default; `--keep` retains them for diagnosis. Its optional
`--measurement-ready-file` lets a coordinator complete preparation first and
release timing only after other workloads stop. T3 now includes the exploration
that was invoked separately immediately after T3 in the recorded run.
