# MR-05 implementation checkpoint — 2026-09-25

MR-05 is in progress. This checkpoint records the implementation contract, not
final acceptance or deployment certification. MR-01 through MR-04 are complete.

## Requirements and retained evidence

The Go typed-context owner accepts the existing version-1 requirement set, with
optional explicit roles. Deterministic templates cover `current_state`,
`comparison` (at least two required subjects), `temporal_change` and
`procedure_application`. An unrecognized shape remains unknown. Task revisions,
subject/relation obligations and optional roles remain bounded and strictly
decoded; callers cannot insert expected answer IDs.

A temporal requirement expands into current state, historical predecessor and a
stated temporal anchor. The predecessor must be connected by the canonical
assertion owner's predecessor identity, belong to the same subject/relation and
have coherent belief/valid-time boundaries. A matching episode or similar text
cannot establish this link. Predecessor identities are projected only when that
predecessor is also eligible in the caller's scope. Explicit historical reads
can inspect superseded assertions; current reads cannot.

Procedure application requires the retained reviewed procedure and a matching
active instruction/policy. Claim support, counterexample and source-group roles
remain distinct. Source groups use the bounded MR-04 canonical lineage projection
in a repeatable snapshot, withholding unavailable origins. Independent support
remains unavailable without an owner certificate; copies and source counts cannot
satisfy it. MR-04's shipping owner does not issue independence certificates.

Coverage is recomputed after final typed and outer-host packing. Omitted required
evidence becomes `budget_dropped`. An earlier conflict or unavailable role cannot
be cleared by omitting evidence during repacking. Source versions remain subject
to the canonical dispatch fence; a diagnostic complete verdict grants no release
permission. Completeness describes declared requirements, not answer correctness
or the completeness of the planner itself.

## Opt-in host recovery

`execute_recovery: true` on `memory.assemble_typed_context` opts into execution.
It additionally requires authenticated user authority from the host's separate
command context. Request arguments and external plugin principals cannot supply
that authority. Without the flag, plans remain proposals only.

The host admits one round of local canonical reads, intersecting requested work
with ceilings of 16 new items, 4096 tokens, 2000 milliseconds and zero external
model cost. The token cap uses a conservative byte bound including serialized
items and source proofs. Existing channel and final context limits still apply.
Recovery can look up exact current roles, canonical source-chain members,
reviewed procedures and counterexample evidence spans. It grants no arbitrary
external tool execution. Unavailable index/source contracts and uncertified
independence remain explicit gaps rather than guessed results.

A separate metadata-only transaction commits the reservation before any recovery
work. The schema-43 `memory_evidence_recovery` table stores principal-isolated task
hashes, requirement digests, bounded outcome metadata and duplicate-attempt counts,
not query text or evidence payloads. A pending reservation survives cancellation,
outer transaction rollback and process restart. It cannot be replayed as a fresh
round. A further round needs a new host-admitted task revision.

Outcomes are generated by the owner from actual scoped reads and measured work;
there is no caller-provided success or result-ID import. Recovered candidates go
through the same packer, coverage evaluator and source-release contract. Exhaustion
leaves the unresolved gap visible. Indexed-code expansion without an admitted
versioned source contract is not automatically executed by this rollout.

## Validation so far

Focused tests cover coherent/false timelines, comparisons, optional obligations,
procedure constraints, copy-based independence refusal, outer packing, actual
canonical correction/revocation and host admission. PostgreSQL recovery tests
cover successful retrieval, token/item/latency caps, restart/rollback persistence
and eight concurrent attempts admitting exactly one round.

The frozen MR-05 evaluation separates coverage from a deterministic retained-object
reader: zero false-complete cases among nine intentionally incomplete fixtures;
reader answer-set accuracy is 6/11. This is a narrow deterministic baseline, not a
model answer-quality claim. Gold objects stay exclusively in the evaluator.
