# PII and Vault qualification — 2026-11-14

**Audit completed; privacy qualification failed. The release is blocked.** PII must be held in
Vault, with opaque references in memory and derived material. Refusing a write without establishing
Vault custody and a memory reference is a failure of that contract. The earlier upgrade guide and
refusal-based interpretation were wrong and have been corrected.

The exact inputs, image identities, outcomes, evidence digest and cleanup are recorded in
[the machine-readable report](pii-vault-2026-11-14.json). Application source was `3549afb7c`; the
private runtime bundle was unchanged. The later changes correct documentation and record evidence;
**they do not implement the missing runtime privacy routing or key-loss repair**.

A new privileged Debian 13 LXC, CT9474 on `192.168.1.253`, hosted real shipped Server and KB
compositions with LUKS-backed PostgreSQL. Inputs and credentials were synthetic. Provider probes
used owned endpoints; the processing pipeline used the pinned real E4B model and embedder. No
production data or other workloads were repurposed.

| Ordinary content-write outcome | Server | KB |
| --- | ---: | ---: |
| PII cases tested | 18 | 18 |
| Encrypted Vault custody plus opaque memory reference | 0 | 0 |
| Raw value retained in memory | 9 | 9 |
| Refused without Vault custody/reference | 9 | 9 |

The matrix covers contact addresses, phone formats, IPv4/IPv6, identifiers, credential patterns,
keys, payment-card-shaped data, postal addresses and names. It is a finite matrix, not a complete
PII classifier qualification. Server key and text-metadata admission were also exercised.

1. **Ordinary writes do not route PII into Vault.** Recognized inputs such as email and credential
   patterns are refused. Other PII, including tested phone and IP forms, is admitted raw. Read-only
   inspection of the actual encrypted fixture Vaults found the known credential controls, but none
   of the submitted PII values. Native logical journals and content files retain the admitted PII.
   The optional protected-intake lane does not make ordinary writes automatic protected writes.
2. **Raw PII reaches vector input.** The actual processing worker published five sources through
   the real model pipeline. A read-only Python profile observer saw five calls to the real
   embedding implementation and the raw phone canary in one input. No manual embedding control
   request was used in that pipeline fixture. TLS, provider identity and vector outputs were
   unchanged. A separate successful graph-tool continuation omitted the phone; that later outcome
   does not protect the earlier embedding input.
3. **Canonical ingress is another unprotected boundary.** Raw original email and password inputs
   reached the controlled model endpoint in successful runs. The Server SQL dump and on-disk bus
   capture contain those input canaries. The tested ordinary Server/KB Docker text logs contained
   no submitted canary. Capture files and canonical persistence must not be confused with those
   text-log results. Matched persistent backups also contain raw PII.
4. **Default software custody needs independent backup protection.** Vault credential canaries
   were absent from raw credential files, Native journals and raw backup scans. Vault files were
   owner-only mode 0600, owned by UID 1000; application metadata contained no test credential.
   Actual attested credential use succeeded and foreign handles were denied. However, the software
   master key is stored beside the ciphertext. Offline decryption of the owned fixture with that
   co-located key recovered the known credential, without a live service. A complete unencrypted
   copy is recoverable, not self-protecting against theft. Public deployment guidance now states
   this boundary. PostgreSQL bootstrap role passwords remain in its own container metadata as
   documented; the LUKS passphrase follows its separate Vault path.
5. **Missing-master handling is defective.** With existing encrypted credentials present, making
   the master key unavailable in an isolated restored copy caused a different master file to be generated.
   Service remained unavailable and encrypted credential files were unchanged. Restoring the
   original key recovered healthy service, credential use and the original memory version. The
   missing key must remain unavailable rather than be silently replaced.
6. **Retained-history policy needs a Vault lifecycle review.** Source inspection of
   [the delete handler](../../src/server/server_vault.c) and
   [the backend retirement/removal code](../../src/modules/vault/vault_store.c) shows mutable entry
   removal and immutable tombstones that replace encrypted values. This is a source-audited gap,
   not a destructive test: no application record or Vault credential deletion was invoked.

Matched persistent snapshots restored successfully into isolated Server and KB projects. Both
retained the original memory content/version and working credentials. Ephemeral TLS material was
regenerated under the original tmpfs requirements. Corrupting a copied credential's GCM tag refused
service readiness and caused no provider effect; restoring the authenticated entry recovered use.
Original volumes remained stopped while restored copies were exercised.

The ordinary `search_memory` continuation failed both a broad query and a fresh single-record
query. No privacy pass is inferred from that incomplete path. The actual graph-tool continuation
was exercised separately. Default software/file custody was tested; hardware and KMS custody were
not qualified by this run. Earlier fixture failures and their corrections remain in the evidence.

All 76 public lint checks passed after correcting the guidance. The final archive contains 42
hash-verified files, including cleanup confirmation, and passed its secret scan. Raw inputs,
credentials, keys, controller state and backup contents were not exported. CT9474, its config and
root disk were deleted, with no remaining crypt mappings or loop attachments. No image was
published and no release was promoted.
