# Memory implementation boundary

Aimee retains its generic memory SDK and host/module transport. Memory records, retrieval and lifecycle are served by a separate implementation: the private aims-db database and its Aimee memory frontend. Their source is not in this repository. From 1.1.0 the application image carries them as a vendored binary bundle ([`vendor/aims-memory`](../vendor/aims-memory/README.md)): prebuilt bridge objects linked into the Server and KB resources, the memory executables, and the scripts that provision an installation.

Each deployment provisions its own installation. The one-shot `aimee-memory-init` service generates the instance's memory identity, grants and owner key at first start, verifies them on later starts, and prepares the installation again after an image update while keeping the stored memory. The application mounts the prepared installation read-only; records, configuration and the owner key live in the instance's home volume. [Deployment](DEPLOYMENT.md#memory) describes the volumes, backup and limits, and the [memory module](modules/memory.md) the commands and tests.

The public tree still builds an explicit unavailable adapter. It is what runs when no installation has been provisioned, for example on a platform without a bundle: it never attaches, opens storage, advertises stages, or falls back to a built-in datastore, and the instance reports `missing_module: memory`. Availability depends on the implementation's actually declared contracts. Similar stage numbers do not imply legacy ABI1/2/4 compatibility.

The old Go implementation and its evaluation/test assertions are preserved as the immutable private aims-db experiments/legacy-aimee-go baseline, with separate consumer sidecars. That baseline is experimental comparison material and is never a default or runtime fallback. Historical decisions remain in [migration history](validation/memory-migration-history.md).

Public CI tests the unavailable adapter, the generic SDK, canonical DB1 producers/access/erasure/replay, the PostgreSQL provider, the bundle's integrity and staleness check, and the provisioning command's decisions. It does not build or test the implementation's source. The bundle is tied to the exact public files it was compiled against, recorded in `vendor/aims-memory/bundle.json`; a change to one of them needs a rebuilt bundle before it can merge. Old MR18 and transitional serving-owner certification are explicitly unavailable after extraction; their frozen manifests remain unchanged.
