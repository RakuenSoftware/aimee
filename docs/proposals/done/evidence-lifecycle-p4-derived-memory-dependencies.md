## Problem and boundary

Derived knowledge, summaries, patterns, preference projections, entity profile
cards, "mental models", is prose that *asserts* something about a factual basis
it does not name. When that basis moves, the prose does not.

This is the most dangerous quiet failure in the system, because derived items
read as confident and are frequently the highest-value thing recall surfaces. A
summary that said "the team deploys on Fridays" outlives the correction that
moved deploys to Tuesdays; an entity profile card built from twelve observations
survives the invalidation of the document that produced eight of them; a learned
recommendation about a function survives the rewrite of that function.

At the pin the substrate is close but incomplete: several derived surfaces record
a *bundle* hash or an `input_hash` (enough to detect "something changed") but
none records *which* inputs, at which versions, under which extractor and policy.
A bundle hash cannot tell an operator which input moved, cannot support partial
re-derivation, and cannot answer "what depends on this document" in the direction
P3's blast-radius preview needs.

Boundary: dependency recording and staleness computation for derived items. What
recall *does* with a stale item is a policy this proposal defines but deliberately
keeps conservative; re-derivation scheduling is slice 5 and nothing more.

## Decision

One dependency table, **new**, plus a computed status on every derived item.

```sql
CREATE TABLE IF NOT EXISTS derived_memory_dependencies (
  id                      BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  derived_kind            TEXT NOT NULL,   -- summary | pattern | profile_card |
                                           -- preference_projection | mental_model |
                                           -- lesson | enrichment
  derived_memory_id       TEXT NOT NULL,   -- stringified pk within derived_kind
  input_kind              TEXT NOT NULL,   -- document | document_version | assertion |
                                           -- memory | code_unit | outcome | entity
  input_id                TEXT NOT NULL,
  input_version           TEXT NOT NULL DEFAULT '',  -- version_no / edge version / generation
  source_hash             TEXT NOT NULL DEFAULT '',
  extractor_version       TEXT NOT NULL DEFAULT '',
  derivation_policy_version TEXT NOT NULL DEFAULT '',
  contribution            TEXT NOT NULL DEFAULT 'supporting'
                          CHECK (contribution IN ('essential','supporting')),
  created_at              TEXT NOT NULL,
  UNIQUE (derived_kind, derived_memory_id, input_kind, input_id)
);
```

`contribution` is the field that keeps staleness from becoming noise. An input
marked `essential` means the derived item does not stand without it; `supporting`
means it contributed. The producer declares this at derivation time. It is the
only moment the distinction is knowable.

### When a derived item becomes stale

A derived item is stale when any of the following holds for a declared input:

1. the input is invalidated (P3, or an assertion invalidation),
2. its source document changed (`source_hash` mismatch, or a new current
   `document_versions` row),
3. a linked code generation is superseded (`code_projection_generations`, or
   `files.hash` differing from the recorded `source_hash`),
4. the extraction or derivation policy version changed,
5. a supporting fact was corrected (the assertion's version advanced),
6. its surviving evidence fell below the threshold its kind requires.

Staleness is **computed, not stamped by a sweep**. The status is a function of
the dependency rows and the current state of their inputs, materialized for
recall performance and recomputed on the P1 events that can change it. A periodic
sweep exists only as a reconciler that must find nothing; if it finds drift, that
is a bug in the event coverage, and it is reported as one rather than silently
repaired.

### Staleness is not deletion

Per derived kind, a staleness policy chooses among four responses:

| Response | When it fits |
|---|---|
| Exclude from recall | An essential input was invalidated and the item is model-derived |
| Down-rank | A supporting input moved; the item is probably still broadly right |
| Show with a re-verification warning | The item is user-facing prose whose removal would be more misleading than its staleness |
| Queue for re-derivation | The inputs still exist and the item is cheap to recompute |

Defaults, deliberately conservative: `mental_model` and `summary` → warn and
down-rank; `pattern` and `lesson` → down-rank and queue; `enrichment` and
`profile_card` → queue for re-derivation. Nothing deletes. A kind that wants
exclusion states it explicitly in its policy, and that policy version is itself
one of the recorded dependencies.

### Direction matters

The table is queried in both directions and is indexed for both:

- **Forward** ("is this item stale?"), recall and ranking.
- **Reverse** ("what depends on this document / assertion / file?"). P3's
  blast-radius preview and P2's `preview_revert` dependents list. This direction
  is the reason P3 must not report an empty dependents list before P4 lands.

### Mental models stay derived

The pin's derived profile surfaces are views over sourced assertions, not
replacement rows, and that discipline is retained. P4 does not turn mental models
into stored assertion rows; it records what a *materialized* derived item was
built from, so the materialization can be invalidated. A derived item must never
be promotable into an assertion by any path in this proposal. That promotion is
an explicit governance decision and belongs to P7.

## Non-goals

- No new derivation, synthesis, or summarization behaviour.
- No automatic deletion of derived content under any condition.
- No re-derivation scheduler beyond a queue with a bounded drain in S5.
- No dependency inference from text similarity. A dependency that was not
  declared at derivation time does not exist; the honest answer is
  "dependencies not recorded", which is what a legacy row reports.

## Owners and dependencies

- **Owner:** kb synthesis, with memory.
- **Depends on:** P1 (events drive recomputation), P3 (document states are inputs
  to staleness).
- **Depended on by:** P3's preview (dependents), P2's `preview_revert`, P5
  (code-generation staleness shares the mechanism), P7, P9 (staleness is a
  reported field).

## Threat and failure model

| Failure | Consequence | Mitigation |
|---|---|---|
| Producer omits a dependency | Item never goes stale; the quiet failure this proposal exists to fix | Derived-kind writers must declare inputs; a derived row written with zero dependencies is recorded as `dependencies: not-recorded` and is excluded from any staleness claim rather than reported as fresh |
| Staleness sweeps drift from event-driven state | Two contradicting answers | Sweep is a reconciler that must find nothing; drift is reported as a coverage bug |
| Over-eager staleness | Recall quality collapses after one document change | `essential`/`supporting` split; conservative per-kind defaults; nothing deletes |
| Legacy derived rows treated as fresh | False confidence on the oldest content | Legacy rows are explicitly `not-recorded`, and are excluded from freshness claims |
| Stale prose still shown without a marker | User acts on outdated synthesis | Warn responses attach a re-verification marker that P9 surfaces in the result trace |
| Dependency table growth | Storage pressure on large corpora | One row per declared input, not per span; growth measured in S5 alongside P1's figures |

## Compatibility and migration

- Additive. Existing derived rows are not backfilled; they report
  `dependencies: not-recorded`.
- New derivations record dependencies from the slice that hooks their producer,
  so freshness claims are true for new content immediately and are never
  retroactively asserted for old content.
- `memory_lineage` is retained; S1 defines whether it becomes a view over the new
  table or is left as a legacy record, and that decision is recorded in the PR
  rather than left implicit.

## Slices

| # | Scope | Done when |
|---|---|---|
| S1 | Table, both indexes, declaration API, `not-recorded` semantics for legacy rows | A derived write without declared inputs is queryable as not-recorded, never as fresh |
| S2 | Hook the summary and profile-card producers; forward staleness for document and assertion inputs | Invalidating a document marks its summaries stale within the same changeset |
| S3 | Reverse query, wired into P3's preview and P2's `preview_revert` dependents | Preview lists exactly the derived items a later execution affects |
| S4 | Code-generation and source-hash staleness for code-derived items; extractor and policy versions | Rewriting a file marks recommendations derived from it stale, keyed on the file's own hash rather than a whole-project heuristic |
| S5 | Per-kind response policies, re-derivation queue with a bounded drain, reconciler sweep, growth measurement | Reconciler finds zero drift on a seeded corpus; growth figures published |

