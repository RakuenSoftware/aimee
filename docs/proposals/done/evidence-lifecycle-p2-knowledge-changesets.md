## Problem and boundary

P1 makes every knowledge mutation an event. Events alone answer "what changed";
they do not answer "what did *this operation* change", and they cannot be undone
as a unit.

The strongest idea available to borrow here is treating graph changes as **commits**: one operation produces one changeset, the changeset
has a diff, and undoing it produces a compensating changeset rather than erasing
history.

At the pin nothing groups writes. One conversation turn can assert four semantic
edges, insert two memories, bind an alias, and stage a provisional rel_type, and
afterwards those eight rows are related only by adjacent timestamps. A document
re-ingest is worse: it can change hundreds of rows with no operation identity at
all, which is precisely why "what did this document add?" is currently
unanswerable and why "undo that ingest" is currently not offered.

Boundary: grouping and reversal of knowledge-object mutations. Document *state*
transitions are P3; derived-item staleness is P4.

commits with a status enum, structured before/after columns per change, a
commit preview, a batch rollback, and an ingest-run rollback. P2's job is to
generalize that shape, not to invent a competing one.

## Decision

Two tables, both **new**, layered directly over P1's events.

```sql
CREATE TABLE IF NOT EXISTS knowledge_changesets (
  changeset_id      TEXT PRIMARY KEY,
  parent_changeset  TEXT NOT NULL DEFAULT '',
  operation         TEXT NOT NULL,        -- turn | ingest | reingest | drain |
                                          -- ontology_promotion | entity_merge |
                                          -- operator_correction | maintenance | revert
  origin_ref        TEXT NOT NULL DEFAULT '',  -- turn_id / doc_key / job id
  actor             TEXT NOT NULL,             -- authenticated principal
  authority         TEXT NOT NULL,
  status            TEXT NOT NULL DEFAULT 'open'
                    CHECK (status IN ('open','applied','reverted','superseded','partial')),
  reversible        BIGINT NOT NULL DEFAULT 1,
  irreversible_why  TEXT NOT NULL DEFAULT '',
  reverts_changeset TEXT NOT NULL DEFAULT '',  -- set on a compensating changeset
  created_at        TEXT NOT NULL,
  closed_at         TEXT NOT NULL DEFAULT ''
);

CREATE TABLE IF NOT EXISTS knowledge_change_items (
  id            BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  changeset_id  TEXT NOT NULL REFERENCES knowledge_changesets(changeset_id),
  event_id      TEXT NOT NULL,          -- the P1 event this item realizes
  object_kind   TEXT NOT NULL,
  object_id     TEXT NOT NULL,
  action        TEXT NOT NULL,
  existed_before BIGINT NOT NULL DEFAULT 0,
  existed_after  BIGINT NOT NULL DEFAULT 0,
  before_state  TEXT NOT NULL DEFAULT '',  -- structured envelope, not prose JSON blob
  after_state   TEXT NOT NULL DEFAULT '',
  revert_plan   TEXT NOT NULL DEFAULT ''   -- the inverse action, computed at write time
);
```

`before_state` / `after_state` hold the object's **envelope**, lifecycle state,
authority, confidence, valid-time bounds, version, in a fixed field order, not
an opaque JSON audit string. The reason is concrete: a revert must restore exact
prior state without reparsing prose, and a reviewer must be able to diff two
changesets without a schema archaeology exercise.

`revert_plan` is computed at write time, while the writer still knows the
semantics of what it did. Deriving the inverse later, from state alone, is where
this kind of system usually goes wrong.

### What one changeset covers

Exactly one of: one conversation turn; one document ingestion or re-ingestion;
one extractor drain; one ontology promotion; one entity merge; one operator
correction; one maintenance sweep. A changeset that would span two of these is a
bug, not a convenience.

Nesting is not supported in P2. A drain triggered by an ingest opens its own
changeset with `parent_changeset` set (a link, not containment) so that
reverting the ingest can report the drain as an affected dependent rather than
silently reverting it too.

### The four operations

- `changeset.show`: the changeset, its actor, status, and its items.
- `changeset.diff`: the envelope-level before/after for every item, plus counts
  by object kind and action.
- `changeset.preview_revert`: what a revert would do: items it would invert,
  items it cannot invert and why, objects changed *since* by another changeset
  (the conflict set), and dependents affected (P4's dependency edges, once P4
  lands; until then, an explicit `dependents: not-computed` marker rather than an
  empty list that reads as "none").
- `changeset.revert`: applies the inverse of each item **as a new changeset**
  with `reverts_changeset` set and `operation='revert'`. The original changeset's
  status becomes `reverted`; its rows are never edited or deleted.

### Rules that make revert honest

1. **A revert never erases.** It composes. Reverting a revert is legal and
   produces a third changeset.
2. **A revert is authority-bounded.** It may not undo a change made under a
   higher authority than the reverting actor holds, the same rule the pin
   already applies to retraction, applied to batches.
3. **A conflicting revert is refused by default.** If an object changed after the
   target changeset, the revert stops and reports the conflict set.
   `--force-partial` applies the non-conflicting subset and marks the resulting
   changeset `partial`, naming what it skipped. Silence about a skipped item is
   the failure mode being designed out.
4. **Irreversible operations are declared, not discovered.** A purge sets
   `reversible=0` and `irreversible_why` at creation. `preview_revert` on it
   returns a refusal explaining why, not an empty plan that looks like success.

### Questions this makes answerable

Each of these is currently unanswerable at the pin, and each becomes a single
query:

- What did this document add?, items of the ingest changeset for that `doc_key`.
- Which facts changed after this agent turn?, items where `origin_ref = turn_id`.
- Why did this relationship become current?, the item whose `after_state` set
  it, its event, its actor and its evidence.
- What would reverting this ingestion affect?, `preview_revert`.
- Which memories depend on the entity merge I am undoing?, the merge changeset's
  dependents (P4).

## Non-goals

- No branching or merging of knowledge states. Changesets are a linear audited
  history with compensation, not a DVCS.
- No cross-database changesets. db1 (user memory) and db2 (org memory) keep
  separate changesets; a single operation touching both produces two, linked by
  `origin_ref`.
- No automatic revert. Every revert is an explicit, authorized action; nothing in
  P2 reverts anything on a timer or a heuristic.
- No UI. P7 renders changesets; P2 exposes the four operations.

## Owners and dependencies

- **Owner:** memory / db2.
- **Depends on:** P1 (events are the items' source of truth).
- **Depended on by:** P3 (document lifecycle transitions are changesets), P7, P8
  (ontology migration runs as a changeset).

## Threat and failure model

| Failure | Consequence | Mitigation |
|---|---|---|
| Revert used to launder history | Audit trail rewritten | Compensating changesets only; originals immutable; both appear in every listing |
| Lower authority reverts a higher-authority write | Authority bypass by batch | Authority-bounded revert, checked per item |
| Blind revert over later edits | Silent data loss | Conflict set computed and refused by default; partial reverts must name skipped items |
| `revert_plan` derived incorrectly for an exotic action | Corrupt restore | Plan computed at write time by the writer that knows the semantics; a plan-less item makes the changeset non-reversible rather than best-effort |
| Changeset spanning two operations | Unrevertable blob | One-operation rule enforced at open; a second `operation` on an open changeset is an error |
| Long-running ingest holds an open changeset | Lock pressure, partial visibility | Changesets are opened per transaction batch; an ingest producing many batches produces many changesets sharing `origin_ref` |

## Compatibility and migration

- Additive. P1 events written before P2 have `changeset_id=''` and are readable
  as ungrouped history; they are never retro-grouped by guesswork.
- `db2_entity_unmerge` and the code-projection generation machinery keep working
  unchanged; S4 routes them through changesets so the two reversal mechanisms
  stop diverging, without removing the existing entry points.

## Slices

| # | Scope | Done when |
|---|---|---|
| S1 | Tables, open/close API, one-operation rule, `changeset.show` | A turn's writes land in one changeset with correct actor and status |
| S2 | `changeset.diff` and envelope capture for assertions and memories | Diff of a correction shows the exact envelope transition |
| S3 | `revert_plan` capture, `changeset.preview_revert` with conflict set, refusal on irreversible | Preview of a purge refuses with a reason; preview over a later-edited object reports the conflict |
| S4 | `changeset.revert` as a compensating changeset; route entity merge/unmerge and ontology decisions through it | Revert of an ingest restores prior envelopes and creates a new changeset; original untouched |
| S5 | Ingest-run grouping (`origin_ref` across batches) and CLI/API read surface | "What did this document add" answered in one call for a multi-batch ingest |

## Status and supersession

Supersedes nothing. Generalizes the reversal precedent set by
[typed-fact knowledge layer](../done/typed-fact-knowledge-layer.md) (entity
unmerge) and [code graph intelligence](../done/code-graph-intelligence.md)
(projection generations) into one abstraction over the whole knowledge graph.
