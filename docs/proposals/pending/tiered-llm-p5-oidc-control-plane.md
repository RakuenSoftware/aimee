# Proposal: P5 — OIDC control plane: aimee-kb manages aimee-servers

- **State:** proposed (pending — not started). Part of `tiered-llm-offering.md`.
- **Author:** JBailes (drafted by the engineer agent, 2026-07-17).
- **Depends on:** P1 (identity/teams), **P2** (the kb→server mTLS egress channel this proposal reverses, and the `remote_writes`/capability gating it honors), and **P7** (the WORM ledger and CA-behind-vault that anchor the management cert's revocation staples). Shares OIDC/identity work with P1/P4.

## Thesis

Every aimee-server already depends on aimee-kb for org egress (P2), so kb is the org-trusted tier above the fleet. P5 turns that trust relationship around: **aimee-kb manages aimee-servers** — enrolls them, lists them, reads their health, and (policy permitting) drives their admin API — with the operator authenticated by **OIDC**. Management is a first-class capability, not gated on any single wiring detail.

## Goal

1. aimee-kb (and kb-console) connect to the org IdP via OIDC (operator SSO).
2. aimee-servers enroll into a kb **server registry**; kb can list them and read their status and health.
3. From the OIDC-authenticated console, an operator reaches a server's existing admin API (agents, config, health) through kb, with the OIDC identity carried to the server — not collapsed to a shared bearer.

## §0 What already exists (and the gap)

- **OIDC verifier + console SSO** — `src/kb/auth_oidc.c`, `kb-console/auth.go` (RS256/JWKS, break-glass path). "Connect kb to OIDC" is largely built for humans already.
- **PKI + enrollment** — `src/kb/enroll.c`, `src/kb/pki.c`: single-use `aimee://` tokens, CSR→CA-signed `cert:CN`. Enrollment today flows **client→KB**; P5 reuses this machinery to enroll **servers into a registry**.
- **Server admin API, per-server** — `src/server/server_http_routes.c:1770+`: `/v1/agents`, `/v1/agent/{add,remove,enable,disable,set,…}`, `/v1/config/{get,set}`, health, delegate, cron — gated by bearer/scope/`remote_writes`.
- **Three real gaps** (from the control-plane survey):
  1. **No server registry / no KB→server management channel.** KB is a callee; its only outbound to servers is a cache-invalidation push (`src/kb/kb_curator_notify.c`).
  2. **OIDC identity terminates at the console** — `kb-console/proxy.go` forwards only the shared `console-admin` bearer ("the browser's own token is never forwarded"); it never reaches a server.
  3. **kb-console's allowlist is KB-only, deny-by-default** (`kb-console/acl.go` + `src/kb/http/kb_route_acl.c`) — it cannot address a server route.

## §1 Server registry (kb-side)

A `server` registry table in DB2: `{server_id, cert_cn, mgmt_cert_cn, owner (OIDC sub, nullable), team_id, last_seen, health, version, endpoint}`. **Every aimee-server has its own individual, role-scoped mTLS credentials** — issued from kb's CA via the existing `aimee://` flow (`kb_enroll_mint` / `kb_enroll_redeem_csr`), each with a unique `cert:CN` and independently revocable (`cert.revoke`). Because the fleet uses TLS in *both* directions with distinct EKU profiles (`clientAuth` vs `serverAuth` — see P8 §0), the roles do **not** share one certificate: a server holds a **`clientAuth` leaf** for its server→kb egress/heartbeat calls (`cert_cn`, the registry key) and a **`serverAuth` leaf** for the management listener kb dials (`mgmt_cert_cn`, §2); kb in turn holds its own **`clientAuth` leaf** for calling servers. Each role cert is issued through the enrollment CA with its **own CSR + proof-of-possession** (the server proves control of the corresponding private key): the `clientAuth` leaf via the existing `aimee://`→CSR flow, and the `serverAuth` management-listener leaf via a parallel CSR carrying a `serverAuth` EKU request — distinct key material and distinct PoP, so neither role's key can stand in for the other. The redeemed `clientAuth` `cert:CN` is the server's identity and the registry key; redemption inserts the registry row and records both role CNs. No shared/fleet cert and no dual-purpose cert spanning both TLS roles — revoking or rotating one server (or one role) never touches another. Servers heartbeat over mTLS, reusing the existing server→kb `/v1/health` client in `kb_client.c`, to keep `last_seen`/`health`/`version` fresh. The `owner` (OIDC sub) is recorded when OIDC is configured and left null otherwise — the registry does not depend on OIDC. The registry is a Postgres/DB2 table (invariant #9): any of the N stateless kb instances serves registry reads and accepts heartbeats, and Postgres is the single authoritative view of the fleet — no instance holds registry state locally. It is a **tenant table under invariant #10**: RLS / team-scoped predicates apply to registry CRUD **and** fleet-management reads — an org-admin sees the whole fleet, a team-lead sees and manages only its own team's servers, and a cross-team registry read/write is denied at the DB layer. Heartbeat writes and **authorization-sensitive registry reads** go to the **primary**. kb selects a server's `endpoint`, its `mgmt_cert_cn`, **and** its revocation status in a **single consistent primary read** (one snapshot) — no TOCTOU between choosing the target and validating it, so it cannot dial a decommissioned endpoint with a stale pin. And there is **no trust-on-first-use**: the `mgmt_cert_cn` is fixed at **enrollment** (the serverAuth CSR + proof-of-possession, above), so kb pins the enrolled cert, never whatever answers the first handshake; the endpoint also passes address-policy validation and the revocation check **before kb's first dial**. Only non-authorization fleet dashboards may read replicas. The registry `owner` field is descriptive metadata only — egress and every authorization decision resolve identity via P1's composite contract, never the registry `owner`. The "single consistent read" is a `REPEATABLE READ`/`SERIALIZABLE` transaction (or one row-returning query) so `endpoint`/`mgmt_cert_cn`/revocation cannot skew. The registry is `FORCE ROW LEVEL SECURITY` under the non-owner runtime role (P1 §1). Enrollment is **idempotent, not falsely atomic** (a DB transaction cannot make external CA signing + two-cert issuance atomic): a `pending` registry row is inserted first under a uniqueness constraint on `(server_id)` and the redeemed CSRs' `(cert_issuer, cert_serial)`, the two role certs are signed (retryable by the same single-use token), and the row is finalized — a partial failure leaves a `pending` row that a retry completes or a sweep expires, never a half-built ambiguous active row. The single-use enrollment token also **binds the team/owner grant at mint time** (an org-admin mints it for a specific team), so a redeemer cannot choose another team's assignment. Each kb **instance** obtains its own per-instance management `clientAuth` leaf by **auto-enrolling at boot via its platform workload identity** (the same identity that unseals the vault) — no shared fleet key, no manual per-instance step; the leaf is individually revocable.

## §2 kb→server management channel

An outbound client from kb to a registered server (mirror of the existing `src/server/kb_client_mtls.c` transport, reversed). **This channel is always mTLS, both directions:** kb presents its own **`clientAuth`** cert and pins the server's **`serverAuth`** management-listener cert (`mgmt_cert_cn`) from the registry (§1) — never bearer-only, and never the same certificate the server uses for the server→kb direction. **At scale each kb *instance* holds its own per-instance management `clientAuth` leaf** under a dedicated management EKU/policy — not one shared fleet cert — individually revocable, so revoking or rotating one instance never touches another; the server validates the CA policy/EKU **and** the kb cert's current primary-backed / stapled revocation status per request, accepting a kb management caller only under that dedicated policy. The server authenticates kb as a `cert:CN` principal with a management scope and honors it under its existing `remote_writes`/capability gating (`server_http.c:334-395`), so the server remains authoritative over what it permits. Certificate revocation is enforced **per request in both directions** of this pooled channel (the series-wide rule, invariant #2 / P1 §2): a revoked management `cert:CN` — kb's `clientAuth` or the server's `serverAuth` — stops authorizing on its next request over an already-established keep-alive connection, not only at the next handshake. Because the user-run server cannot read DB2 — and a TTL-cached status list would leave a stale-cache window that violates the per-request promise — kb **staples a fresh, short-lived signed status to each kb→server request** (OCSP-stapling style: a signed "this mgmt `cert:CN` is not revoked as of <recent generation/timestamp>", pinned to kb's CA). The server verifies the staple's signature and freshness **per request**, so a revoked kb cert — which can no longer obtain a fresh staple from the primary-backed revocation source — stops authorizing on its **very next request**, with no stale-cache gap. The staple's freshness is anchored two ways, kept **distinct from the vault's key-rotation epoch** (that primitive is for anti-rollback of *keys*, not cert revocation — conflating them was wrong): (i) a **dedicated monotonic revocation-status generation** that advances whenever the revocation list changes, signed by kb and non-rollbackable (the server rejects any generation below the highest it has seen); and (ii) — for a true per-request guarantee — a **server-issued challenge**: the server includes a fresh nonce in its request, and kb returns a status **signed over that nonce**, so a captured staple cannot be replayed on any later request. A revoked kb cert can no longer obtain a nonce-bound fresh staple, so it stops authorizing on the **very next request**. **The staple is signed by a dedicated online status authority — not by every unsealed kb.** The status-signing key is a **distinct, narrowly-scoped credential** held by a small primary-backed revocation-status service (its own key slot under P7 custody), **not the general kb CA signer that any unsealed kb instance can invoke** — so a revoked or compromised kb cannot self-mint a fresh staple even while holding an unsealed vault. The exchange is a complete challenge round-trip with a defined ordering: **(1)** the server issues a fresh **nonce**; **(2)** the kb instance forwards it to the status authority, which **queries the primary for current revocation state** and, only if the caller's cert (issuer+serial) is unrevoked, returns a status **signed over `(nonce, peer-cert issuer+serial, target-server-id, purpose, current revocation-generation)`**; **(3)** the server verifies that signature, its freshness, and that the generation is ≥ the highest it has seen. A kb whose cert has been revoked **cannot obtain a signature** (step 2 refuses it), so it fails on its very next request. If the status authority is unreachable the server **fails closed** — it rejects the management request rather than accept a stale or self-signed staple. The revocation-generation is stored primary-authoritatively and is monotonic (§1); integration tests cover a revocation landing **between challenge and action** on a live keep-alive connection. (Symmetrically, kb checks the server's `serverAuth` cert against its own primary-backed revocation per request, §1.) No new auth model on the server — just a new trusted mTLS caller. (The mgmt listener's bind/port is a build-packet detail: a distinct authenticated listener, not the data-plane port.) **Endpoint anti-SSRF:** the registry `endpoint` is supplied by a user-run server, so kb dials it only when it (a) presents the registered `mgmt_cert_cn` on the mTLS handshake — a cert pin that defeats DNS-rebinding and redirect-to-another-host — and (b) passed enrollment-time endpoint-policy validation (allowed address ranges, no link-local/loopback/metadata addresses). The deny policy is concrete and **covers IPv4 and IPv6**: RFC1918 + `169.254.0.0/16` + the cloud metadata IP `169.254.169.254`, loopback, and IPv6 `::1`/`fe80::/10`/`fc00::/7` + IPv4-mapped forms. Against **DNS rebinding**, kb **resolves and re-validates every candidate address at connect time** (not only at enrollment) and pins the connection to the validated IP; kb never follows redirects on this channel. **Residual trust, acknowledged and bounded:** the `endpoint` is user-registered, so kb dialing it is a deliberate, bounded trust — the `serverAuth` cert pin + address policy + no-redirect + per-request revocation contain *where* kb connects, and the mgmt channel can do nothing the target server's own `remote_writes`/capability policy does not already permit, so a malicious `endpoint` cannot escalate beyond the server's own authority. The revocation/endpoint-policy check is revalidated **on the dialing connection itself** (the mgmt cert's per-request staple), so a revocation landing in the check-then-dial gap is caught at connect. The per-request staple is **bound to a fresh server-issued nonce/challenge** for that request (the server-issued challenge established above — kb never mints its own nonce here), so a captured staple cannot be replayed on a later request. OIDC, when present, only names the *operator* behind a kb-originated action (§3); the channel itself never depends on it.

## §3 OIDC identity propagation

Stop collapsing identity at the console. When an operator drives a server action, kb mints a **short-lived, kb-signed JWT** carrying the operator's identity, with a defined contract: **issuer** = kb, **audience** = the target server, **subject** = operator (OIDC `sub`, or owner/bearer id), **capabilities/scopes**, issued-at/**expiry**, a unique **`jti`** for replay rejection, and **binding to the authenticated kb management `cert:CN`**. The server verifies every one of these before honoring the action, so it records *who* acted rather than a shared `console-admin`. (One signed token type verified server-side — not a per-action certificate.) Replay rejection is **server-local**: the management token is audience-bound to exactly one target server, and that server (which verifies and consumes it — the kb→server direction) keeps a small recently-seen `jti` cache bounded by the token's short TTL, deduping locally **without touching DB2** (servers never access DB2). The JWT signing key carries a `kid` with defined rotation (publish new `kid`, accept both during an overlap window, retire the old) and revocation (drop a `kid`); the server fetches kb's public verify keys by `kid` from kb's **JWKS endpoint over the *server→kb* channel** it already trusts via its own `clientAuth` cert (HTTPS, pinned to kb's CA) — **not** over the kb→server mgmt channel, which would be circular (the server would need to verify a mgmt token to fetch the keys that verify mgmt tokens). kid rotation publishes the new key while keeping the **previous kid still trusted** through an overlap window, so an in-flight token is never orphaned. Both token types — this kb→server management JWT and the server→kb **telemetry actor token** (aud = kb, P9 §2, minted by kb when a human authenticates to it) — are signed by the **same kb token-signing key** (`kid`-versioned) and separated only by `audience`/direction: the server verifies the management JWT, kb verifies the telemetry token. On an unknown `kid` (kb rotated the signing key), the server **re-fetches JWKS once** before rejecting, so a mid-rotation token is not spuriously refused. **Signing-key *revocation* is fail-closed for already-known kids too:** the JWKS cache has a **bounded validity** with mandatory authenticated refresh, and the key set carries a **signed, non-rollbackable generation** (the same custody primitive as P7 anti-rollback) that the server checks on every management request — so dropping a `kid` at kb stops it being trusted within the bounded window, and immediately once the generation advances, rather than indefinitely because a server cached it. That identity is the operator's OIDC `sub` when OIDC is configured, and the owner/bearer/console-admin identity otherwise — the propagation mechanism is the same in both cases. This closes gap (2) and gives the server-side audit log a real actor without requiring OIDC. **kb also keeps its own authoritative record:** because the target server is user-controlled, its log is not the authoritative account of a privileged action — kb appends a **tenant-scoped, primary-written WORM management audit event** (the P7 §6 ledger) for every action it originates: authorization decision, target server, actor composite identity, capability, token `jti`, request digest, result, and correlation id (no secrets or raw config) — so the org control plane has a tamper-evident record independent of the user-run server. **Crash-safe ordering:** kb appends the WORM **intent** record (append-only, P7 §6) *before* dispatching the irreversible remote action, and the **outcome** after — so an action can never execute without a durable kb record; the actor is the **composite, tenant-qualified identity** (`(iss,sub)` or cert-serial identity + team, P1 §2), not a bare `sub`. The server additionally verifies the JWT's `cert:CN` binding **against the mTLS peer cert actually presenting it**, so a token cannot be replayed over a different channel. Management-token `jti` replay state is **persisted server-side** (a durable local table, not only in-memory), so a server crash/restart inside the token TTL does not reopen a replay window.

## §4 Console surface

Extend the console allowlist (`acl.go` + `kb_route_acl.c`) with a **server-scoped** family: list servers (registry), view a server's health/agents/config, and — behind an explicit org-admin capability and the target server's own `remote_writes` policy — drive its admin endpoints via §2. New console views: **Fleet** (server list + status) and a per-server drill-down. OpenAPI and `v1-method-coverage` for the new kb routes.

## Acceptance criteria

- A server enrolls and appears in the registry with its `cert:CN`, owner, team, version, and a fresh heartbeat.
- A server presents a `clientAuth` cert to kb (server→kb) and a distinct `serverAuth` cert on its management listener (kb→server); neither certificate is accepted in the other TLS role.
- An OIDC-authenticated operator lists the fleet and reads a server's agents/health through kb.
- A management action reaches the server as the operator's propagated identity and is recorded as that actor in the server audit log — not as `console-admin`.
- A server with `remote_writes: off` refuses a management write even from kb (server stays authoritative over its own policy).
- Break-glass console login still works if OIDC is down (existing path preserved).

## Testing

**Unit:** registry CRUD, enrollment→registry insertion, identity-propagation token minting and verification, allowlist extension (server routes permitted, others still denied). **Integration:** enroll a real server into a kb, list it, drive an agent enable/disable through kb, assert the actor in the server's audit log, and assert `remote_writes: off` blocks the write.

## Non-goals

No config *push* fan-out or templating across many servers in this packet (registry + single-server drive first; bulk orchestration is a follow-up). No replacing the server's local auth — kb becomes a trusted caller, not the server's owner. No SAML.
